## Project

Astrolabe Studio — a cross-platform (Windows/Linux/macOS) **desktop** app that runs and manages many local Claude Code sessions from one place: projects, agents, notifications, approving or rejecting agent proposals. Think "AgentRoom, but better".

Direction (not built yet): one coordinating Claude that routes user requests to agents in concrete projects; later triggers (GLPI, Jira ticket → agent analyses → proposes a solution → user approves/rejects); long-term it may grow into a full IDE.

**Licensing constraint (hard rule):** everything runs locally against the user's own Claude Code installation. No server-side component that hosts or proxies Claude sessions. Do not design features that need one.

## Stack

- Java 25 on **JetBrains Runtime (JBR) 25** (Gradle toolchain `vendor = JETBRAINS`, provisioned via the Foojay resolver, ~670 MB once): Jewel 0.41 classes are Java 25 bytecode, and JBR gives the custom title bar with native snap/maximize (`DecoratedWindow`). Without JBR the app falls back to the plain OS frame. Spring Boot 4.1, Kotlin 2.4 (UI only).
- Web review needs the JCEF flavour of JBR (Foojay `jbrsdk_jcef`); the build checks it (`verifyJcefRuntime`).
- UI: Compose Multiplatform 1.12 + Jewel standalone (`jewel-int-ui-standalone`). Compose is Kotlin-only, hence the Kotlin source set.
- Storage: SQLite (`sqlite-jdbc`, WAL) in `~/.astrolabe-studio/astrolabe-studio.db` (`astrolabe.data-dir`), schema via Flyway SQL migrations in `src/main/resources/db/migration` (`V<n>__name.sql`, baseline `V1__init.sql`, never edit an applied one). Access through `JdbcClient`, not JPA.
- Gradle (Kotlin DSL) — the Compose plugin owns desktop packaging (`packageMsi` / `packageExe` / `packageDeb` / `packageDmg`), so no Maven.
- Single module for now: `src/main/java` (Spring, domain logic) and `src/main/kotlin` (Compose UI). Package root `com.github.krpkbhdn.astrolabe`; UI in `.ui`.
- Spring runs **in-process without a web server** (`WebApplicationType.NONE`, `headless(false)`); the UI is started from `ui/Main.kt` and calls Spring beans directly.


## Architecture

Packages under `com.github.krpkbhdn.astrolabe` (Java, Spring beans) and `.ui` (Kotlin, Compose):
- `project` — registered project directories (SQLite). `claude.install` — finds the native `claude`, version, login state.
- `claude.hook` — loopback `HookServer` receives Claude Code hooks; `HookSettingsWriter` writes the per-session `--settings` file (merging the overlay settings by allowlist, `.prompt.md` and `.agents` files; all hook events except Setup, Worktree*, MessageDisplay) and the owner-only `<id>.token` file; the per-session token is written literally into the settings and mcp files and read by `HookPoster` from `--token-file`; `HookEventStore` keeps an event log. The statusLine and SessionStart command hooks run the app itself: `ui/Main.kt` hands `--post-hook <url>` to `HookPoster` (java.base only, token from `--token-file`, env `ASTROLABE_HOOK_TOKEN` only as fallback, loopback http only) before anything else starts; `HookHelperCommand` builds the SessionStart exec form and the statusLine shell string (launcher = `ProcessHandle` command, the JBR java in dev), on Windows with 8.3 short paths from `WindowsShortPath` (GetShortPathNameW via FFM). The SessionStart exec form needs Claude Code >= 2.1.139 (`ClaudeVersion`; one re-detection, then SessionStart is omitted with one warn when the version stays unknown), and a Windows statusLine whose launcher path still needs quotes is written only with Git Bash (`GitBashDetector`), otherwise omitted with `unavailableReason()`. `HookPoster` exits 1 with a stderr line for a missing token or non-loopback URL and 0 otherwise (1 s connect, 2 s read).
- `claude.session` — `StatusReducer` (pure) + `SessionRegistry`: per-session status OFFLINE/IDLE(green)/WORKING(yellow)/NEEDS_ACTION(red), subagents. `notification` — status transitions to notifications.
- `claude.proposal` — `ProposalService` holds the pending `Proposal` of each held hook (questions, plan approval, tool permission, MCP form; `ProposalParser`), `answer(id, ProposalAnswer)` renders the hook output, `dismiss` hands the dialog back to the terminal; proposals settled elsewhere (PostToolUse of the tool, Stop, new prompt, Esc, exit) are released. Details in `docs/claude-code-protocol.md` section 16.
- `claude.launch` — `ClaudeLauncher` starts `claude` in a pty4j PTY (with the project's `SessionOverlay` flags, a failure to read the overlay logs only the exception class and launches without it) with `ASTROLABE_SESSION` env and injected hooks (hook directories of live pids are never deleted, only those of dead ones; `launchIn`/`launchTaskIn` start in a project's git worktree folder, validated by `WorkDirectories`); `BackgroundAgentService` wraps `claude agents --json`. The Left-arrow agent view restarts a session with a foreign environment, which is why identity and tokens live in the per-session files and not in env vars.
- `usage` — `RateLimitService` (account-wide 5h/7d `rate_limits`, Pro/Max only) and `SessionUsageService` (per session model, effort, context %, cost from the statusLine payload). `ui/chrome` shows them as the top-bar usage chip with a click-open detail panel (`UsageIndicator`, `UsagePanel`; shortcut Ctrl+Shift+Y, palette "Show usage"); Team plans get an explanation plus the per-session list. Context usage per session: `ContextWindow` (from the statusLine `context_window`), shown as the `ContextMeter` chip in the status bar (yellow above 50%, red above 70%, where a blinking `CompactAlert` offers /compact) and a `ContextBar` on `SessionCard`; click, Ctrl+Shift+X or palette "Show context usage" opens `ContextUsageDialog` (`ContextUsageModel` is the pure view logic, `AppState.contextSessionId`); the dialog lists what fills the window from `usage.context.ContextBreakdownService` (`claude -p --resume <id> --fork-session --no-session-persistence /context`, no model call, cached for `astrolabe.context-breakdown.ttl`).
- `project.ModelSelection` — per-project model and reasoning effort (SQLite), passed as `--model`/`--effort` by `ClaudeCommand`; `ui/screens/ModelControl` in the session tab strip shows the live model/effort and, for a free session, types `/model`, `/effort` (or Alt+P for Claude's own picker) into the PTY via `SessionCommandWriter`; without a live session it edits the default for the next launch.
- `project.TrustLevel` — trust ASK/TRUSTED/AUTONOMOUS: app-wide default ASK (ASK or TRUSTED only, existing projects follow it; `TrustSettingsService`, Settings > Trust; AUTONOMOUS per project only, confirmed in the chip) with a per-project override (NULL = default; `ProjectService.selectTrust`/`useDefaultTrust`, Project settings > General), resolved by `TrustLevel.effective` at launch (SQLite); status bar chip `ui/chrome/TrustIndicator` (pure `ui/trust/TrustIndicatorModel`, `AppState.trust`) shows the effective level and edits the override for the next launch: `claude.hook.TrustPermissions` adds defaultMode and allow/deny rules to the session settings, `claude.proposal.TrustPolicy` (+ `SessionTrust`) lets `ProposalService` auto-allow permission requests without turning the session red; Assistant and groups always ASK. Details in `docs/claude-code-protocol.md` section 22.
- `run` — run configurations per project (SQLite) started from the UI: `RunConfigurationService`, `RunService` (one PTY per run); `run.mcp` holds the MCP tools (`list/set/delete_run_configuration`) served by `claude.mcp.McpEndpoint` on the HookServer, and the bundled plugin skill `run-configurations` (`claude.plugin.ClaudePluginWriter`, `src/main/resources/claude-plugin`) makes Claude register a configuration for its git worktree. Details in `docs/claude-code-protocol.md` section 15.
- `shell` — plain interactive shells like IDEA's Terminal: `ShellDetector` lists installed shells (PowerShell 7, Windows PowerShell, cmd, Git Bash, WSL; `/etc/shells` with `$SHELL` first), `ShellLauncher` spawns one in the project directory (or a validated worktree folder, directory overload) through the shared `claude.launch.PtySpawner`; not a Claude session (no hooks, never in `SessionRegistry`, ids `shell-<uuid>`). UI: `ProjectTab.Shell` tabs, `ShellsState` (labels, per-shell `directories`, last chosen shell in `UiSettings`, tab closes when the shell exits), terminal button in the tab strip, Alt+F12.
- `ui/assistant` + `ClaudeLauncher.launchAssistant` — the Assistant: a Claude session outside any project in `<dataDir>/assistant` (sentinel `ClaudeLauncher.ASSISTANT_PROJECT_ID = 0`, no team/plugin, constant `--append-system-prompt`); `AssistantState` (`AppState.assistant`) starts or focuses the single live one and, only for it, polls the terminal screen for Claude's trust-folder dialog and offers an app confirm (Yes sends Down+Enter); `Route.Assistant`, sidebar item, palette entry, Ctrl+Shift+I; project 0 is routed to the Assistant screen by `AppState.routeOf`; its MCP access is described in `app / app.mcp`. Ctrl+Shift+E (`QuickRequestDialog`, palette "Ask assistant") sends a one-line request to it. `ui/state/AppControlAdapter` implements `app.AppControl` for the UI (each call runs on the UI scope and waits up to `astrolabe.app-control.ui-timeout`). Startup: `AssistantStartupState` asks "Start the Assistant?" once per run after the author offer (checkbox "Don't ask again"), or starts it in the background without navigating; mode `AssistantStartup` ASK/AUTO_START/NEVER in `UiSettings`, cycled by the palette entry "Assistant at startup"; `TerminalHost.sessionOf` reads an observable open counter so `TerminalView` recomposes when the terminal opens after the session appeared.
- `app` / `app.mcp` — assistant app control: `AppControl` is the port the tools use to drive the UI (open project, navigate, attach a launched session, queue a prompt); `AppControlRegistry` holds the connected implementation ("UI not ready" before it). Two physically separate MCP servers share the JSON-RPC core `claude.mcp.McpJsonRpcServer`: `astrolabe` (`McpEndpoint`, `/mcp/<secret>/<session>`, only `McpTool` beans = run-configuration tools, knows nothing of the app) and `astrolabe-app` (`app.mcp.AssistantMcpEndpoint`, `/assistant-mcp`, `Authorization: Bearer <assistantSecret>`, only `AssistantMcpTool` beans; these are not `McpTool`s, so Spring cannot inject them into the project server). The app server has its own per-run secret (`HookServer.assistantMcpToken()`), written only into the Assistant's owner-only per-session mcp file (`HookSettingsWriter.writeAssistant`, literal `Bearer <secret>`), never into the environment; project sessions never get the URL or secret. The Assistant gets an MCP config with only the `astrolabe-app` server (never `astrolabe`) and an `--allowedTools` list of every app tool (`toolNames()` of the `claude.mcp.AssistantMcpServer` interface, implemented by `AssistantMcpEndpoint`), whose own dialog gates every tool except the ones in `AssistantMcpTool.autoApproved()`: read-only or easily undone tools (incl. git_status, git_branches, git_worktrees, git_log, git_diff, git_fetch), auto-approved via the allowlist; remove project, git writes (commit, push, pull, checkout, worktrees) go through the permission dialog. `StartSessionTool` resolves `ClaudeLauncher` through `ObjectProvider` (the launcher chain reaches `AssistantMcpEndpoint`, which needs the tools) and applies the project's default team like the UI. Beyond projects, sessions, runs and git the tools cover groups (`set_group`), resuming sessions, teams, prompt templates, skills, plugins and marketplaces, MCP servers (config output redacted), project presets (read/plan auto-approved, edit and `apply_preset` ask; payload values redacted) and `get_help` (bundled `assistant/help.md`); extension writes always ask, `install_plugin` never auto-accepts a plugin command; `AssistantToolCatalogTest` keeps the protocol doc and help in step. Tool set in `docs/claude-code-protocol.md` section 17.
- `task worktree` — Start Task "Isolated worktree" (`TaskDialogState.start(..., isolated)`) makes `git.TaskWorktreeService` create branch `task/<slug>` in its own folder and a `TaskWorktree` row (`task_worktree`: project, path, branch, base branch, task; no project row). The session starts in that folder under the parent project (`ClaudeLauncher.launchTaskIn`/`launchIn`, `claude.launch.WorkDirectories`; `ShellLauncher` directory overload; `SessionsState.sessionDirectories`, `ShellsState.directories`). The Git tab switches context with `ProjectGits` (`of`/`mainOf`/`switchTo`/`contextsOf`, pure `workContexts` in `WorkContexts.kt`). Local `Merge into <base>` (`GitTaskMerge`): describe, confirm, re-checks, `--no-ff` merge in the folder where base is checked out, abort on conflict, nothing pushed. After a local merge (ancestor check) or a merged PR (`headRefOid` == HEAD) the worktree, branch, run configurations and task row are cleaned up. Create PR is optional (only with a GitHub remote and `gh`).
- `github` — pull requests through the user's own `gh`: `GhCli` reports availability MISSING/NOT_AUTHENTICATED/READY/UNKNOWN (UNKNOWN = could not tell, previous state stays; READY cached for `readyTtl`), `PullRequestService.find` looks up a branch's PR via `gh pr view` and returns a `PullRequestLookup` that tells "no PR" from a gh failure (CI state from `statusCheckRollup`, parsed by `PullRequestJson`), `create` passes `--repo=`/`--title=` as single args (Windows quoting) and the body by file; the title and body draft comes from `git.ChangeDescriptionService` (`ChangeDescriptionProperties`, `astrolabe.git.description`): diff against the fork point incl. uncommitted and untracked files, strict JSON answer validated, one retry then a deterministic fallback, never an error sentence; tunables in `GhProperties` (`astrolabe.github`, e.g. `ciPollInterval`, `readyTtl`).
- `gitlab` — merge requests through the user's own `glab`: `GlabCli` (shares `github.ForgeCli` with `GhCli`; `auth status --hostname <host>`, 401/403/"no token" mean NOT_AUTHENTICATED, an unreachable host UNKNOWN) and `MergeRequestService` (`find` via `glab mr list`/`view`, `create` with the description by file, URL read from stdout or stderr), reported with the pull request types. The UI picks the forge from the push remote (`ForgeRemote`/`forgeRemote`, `PullRequestPort` dispatches on `Forge`): host containing "github" or "gitlab"; other hosts, incl. self-hosted GitLab without "gitlab" in the name, are unsupported (known limitation). GitLab polling reuses `astrolabe.github.ci-poll-interval`; tunables in `GlabProperties` (`astrolabe.gitlab`). Safe worktree cleanup works only through the local merge.
- `workspace` — open folder, open in IntelliJ IDEA, `git diff` parsing.
- `voice` — voice input: hold-Space dictation in text inputs (`ui/voice`: `VoiceDictation` hold detection and session lifecycle, `DictationEdit` pure text edits, `DictationCaret` level bar caret, `DictationStatusRow`; `VoiceTextArea`/`VoiceTextField` wrappers fed by `LocalVoice` from `AppRoot`, shared `components/DictationChrome`; wired into Start Task, assistant request, prompt queue, prompt library, team roles, proposal dialogs, skill description and commit message; `AddServerDialog` and fields where Space is meaningful are left out). Backend: `VoiceInputService` starts a `DictationSession` on a warm `FfmRecognizer` (whisper.cpp through `java.lang.foreign` straight into whisper.dll inside the process, no external executable or child process; one per model/device/language, closed after `idleShutdown` to free VRAM), Silero VAD gates the audio. `NativeRuntime` loads one runtime per process, so switching CPU and CUDA needs an app restart (a CPU request reuses a loaded CUDA runtime); runtimes and models are downloaded only by an explicit `install(...)`, never on start.
- `team` — agent teams (SQLite, "Dev team" seeded by the migration): `TeamService` CRUD and validation, `TeamAgentsJson` builds the `claude --agents` JSON (one native subagent per non-lead role, with model and effort) and the lead's system prompt addendum; `ClaudeLauncher.launchTeam` starts the lead with the lead role's model/effort, `--agents`, `--append-system-prompt` and the task as the first prompt; every launch from the UI (new, `--continue`, `--resume`) also passes the project's default team (`launch(projectId, mode, team)`, project model/effort win per field over the lead's), re-passed on resume because claude does not persist these flags; `WindowsArgument` quotes arguments because pty4j does not escape quotes on Windows. Details in `docs/claude-code-protocol.md` section 11.
- `author` — the author's bundled USER-LEVEL Claude Code setup as a catalog (`src/main/resources/author-profile/profile.json`, `AuthorCatalogService`): separately versioned `AuthorItem`s with area (CLAUDE_TOOLS, CLAUDE_CONFIG), group, kind (marketplace, plugin, skill, MCP server, team, settings fragment merged into the user settings.json), `requires` and per-version change notes; no project scope, no app settings, no Claude handoff session. The app installs every kind itself (a plugin needing confirmation is never auto-accepted). Decision policy (SQLite `author_item_decision`): no row or an older installed version is offered, DECLINED is never offered again, a manual install overwrites a decline; installing never declines the unchecked items, only "Don't offer these" does. UI in `ui/author`: `AuthorCatalogDialog` (min(1040dp, 92% of window) x min(720dp, 86%); areas "Claude tools" and "Claude configuration" with counts of new/updatable items on the left, groups in the middle, cards on the right; one chip at most per card: Update with its change lines, or Declined; installed items show a check and "Installed" and cannot be selected; "Also installs: ..." names requirements not installed yet; search, "Only new and updated"; footer "N selected", Not now, Don't offer these (start offer only), Install N selected), pure `CatalogSelection` (requires closure checks and cascading unchecks that skip installed items, tri-state, search, counts). `CatalogView`/`AuthorProfileState` (`AppState.author`): the start offer once per run preselects new and updated items (a team that would replace an existing one stays unchecked), manage mode (palette "Author configuration", Settings page "Author setup") preselects nothing; Not now/Esc record nothing. Project presets are a separate feature (`preset` package).
- `overlay` — the app's per-project config outside the repository, in `<dataDir>/projects/<projectId>/` (`ProjectOverlayService`, `ProjectOverlay`: `mcp.json`, `settings.json`, `instructions.md`, `agents/*.md`, `context/.claude/skills/**`; one JSON reader `readObject`/`readObjectLenient`; writes only through `ProjectOverlay.write`: containment check, owner-only dirs and files via `OwnerOnlyFiles`). `extension.ProjectOverlays` is the one lookup by folder (registered project or group, or the parent project of a task worktree folder). A launch reads it into a `SessionOverlay` and passes it as flags, never touching the project: servers join the session `--mcp-config`, instructions (after the team lead addendum) go to the per-session `<id>.prompt.md` through `--append-system-prompt-file`, agents join `--agents` (above `astrolabe.overlay.max-agents-json-chars` of escaped size they travel as a per-session plugin directory `<id>.agents` and appear as `astrolabe-overlay-agents:<name>`), skills come from `context/` through `--add-dir`, settings through `--settings` by an ALLOWLIST: only `enabledPlugins` and `permissions.deny`/`ask` (defaultMode, allow, env, helpers, hooks and the rest are dropped). The session denies Edit on the overlay folder and Read of its `mcp.json` and `settings.json`; a Bash redirect cannot be blocked. A group merges its own overlay, then its members' in order (first name wins, member server paths absolutized); a group that overrides LSP takes no LSP plugin and no `lsp-navigation` note from its members unless its own plugins keep LSP; group Code Mode has an effective value from the members or its own override. Overlay MCP servers start with no Claude approval dialog, so stdio MCP preset components need confirmation and the Assistant `add_mcp_server` asks. A project's overlay is deleted with it (`ProjectService.subscribeRemoval`); the startup sweep removes only orphans older than `astrolabe.overlay.sweep-grace` and never when no project is listed. `claude -p /context` runs without overlay flags (known limitation: its breakdown omits overlay instructions, skills and agents). Details in `docs/claude-code-protocol.md` section 23.
- `preset` — project presets (SQLite): `ProjectPresetService` CRUD with revisions (every change to a preset or its components raises `revision`) over components of kind MARKETPLACE, PLUGIN, SKILL, AGENT, MCP_SERVER, INSTRUCTION, SETTINGS, FILE (JSON payload per kind, validated by `PresetComponentValidator`); the bundled presets are layers from `BundledPresetLoader` (`presets/presets.json`, synced at start, restorable): `general`, `frontend` (includes general; Playwright and frontend-design as local plugins from `claude-plugins-official`, an instruction), `angular` (includes frontend; MCP `angular-cli` via `npx -y @angular/cli mcp` without --read-only, which only drops devserver_start/stop and run_target; vendored skill `angular-developer`, MIT, 40 files, pinned to angular/skills commit fc26b37abf2b6e9aeec3a57b6568453bcac2b8b6); an entry may carry `includes` (flattened at load, dedup by kind+name, own components override, a cycle or unknown key fails fast) and `match` (traits); stored presets stay flat; Java/Node/React/Vue have no layer (LSP covers languages, no stack tools worth shipping). `TechnologyDetector.detectMarked` (marker table by trait, same bounded scan) and `preset.PresetRecommendation` (traits angular, frontend; most specific layers; general always) pick the recommended layers. `preset.apply.PresetApplyService` applies a preset to a project folder without a Claude session: `plan(List<Long> presetIds, dir)` (several layers merged by (kind, name), first layer wins) gives one `PlannedChange` per component (CREATE, UPDATE, INSTALL, PRESENT, CONFLICT, NEEDS_CONFIRMATION, optional preview text), `apply(projectId, presetIds, dir, selectedIds)` re-plans, then runs the selected writable ones through one `PresetComponentApplier` per kind (marketplaces, plugins, MCP servers, skills/agents/files, instructions, settings last; one failure never stops the rest; a plugin needing confirmation is reported, never auto-accepted; an MCP server needing a sign-in is `SIGN_IN_NEEDED`). Everything but FILE components goes into the project's overlay (see `overlay`), never into the project folder: instructions are managed blocks between `<!-- astrolabe:begin <slug> -->` markers in the overlay `instructions.md` (replaced only inside their own markers by `ClaudeMdSections`; a same-titled hand-written section is a CONFLICT), skills under `context/.claude/skills`, agents in `agents/`, settings fragments and plugin enablement in the overlay `settings.json` (merged atomically through `ProjectOverlaySettings.update`); the payload `scope` ("local") is still validated but no longer selects a target. A stdio MCP server component is NEEDS_CONFIRMATION (reason: see `overlay`; the preview shows command and args), a remote one is INSTALL. `McpServerApplier` wraps a bare `npx` command as `cmd /c npx` on Windows at plan/apply time (stored presets stay platform neutral). `preset.apply.TidyClaudeMd` (resource `preset/tidy-claude-md.md`) backs the Result step's "Tidy with Claude"; it still targets the in-project CLAUDE.md/CLAUDE.local.md (old files) and says app-managed settings live outside the project. `PresetApplicationService` keeps which revision each project applied (`project_preset_application`: Applied, or Outdated when the preset revision is newer) and whether it declined the offer (`project_preset_offer_declined`); the application is recorded when something was applied or everything was already there.
- `ui/presets` — Settings page "Project presets" (`PresetsPage`/`PresetsState`: list, tabs per component kind, one dialog per kind) and `ui/presets/apply`: `ApplyPresetState` (`AppState.applyPreset`; plan and apply run off the UI thread) drives `ApplyPresetDialog` with three steps, Choose (searchable preset layers, several selectable, `PresetRecommendation` ones preselected with a "Recommended" chip, Applied/Outdated chip for this project), Review (plan grouped by kind with checkboxes, expandable preview, header summary; PRESENT unchecked, CONFLICT and NEEDS_CONFIRMATION disabled) and Result (outcomes, sign-in and confirm notes, and "Tidy with Claude": an explicit click starts a normal interactive Claude session, never headless, with a fixed prompt to merge same-meaning sections of the in-project CLAUDE.md/CLAUDE.local.md after showing a plan; asking before editing is prompt text only, trusted projects do not enforce it); pure logic in `ApplyPresetModel`. Entry points: "Apply to project..." on the preset page and palette "Apply preset to project" (a `ProjectPickerDialog` first when no project is current), project menu "Apply preset...", and the offer: `PresetOfferState` (`AppState.presetOffer`, started from `AppState.navigate`) asks "Set up <project>?" once per run for a project without any application or decline, preselects the recommended layers ("Recommended" chip), never while another dialog is open (`dialogBlocksOffer`); Review & apply opens the review, Not for this project declines for good, Later records nothing.
- `toolchain` — language-server tools for Claude Code LSP plugins installed from the app: bundled catalog `src/main/resources/toolchain/tools.json` (`ToolCatalog`, `ToolDefinition`: kinds PREREQUISITE / LANGUAGE_SERVER, per-OS install argv, markers; `ToolCatalogValidator` is fail-fast: installer + verb allowlist, no shell metacharacters or elevation, plain binary names). Languages: TypeScript/JavaScript, CSS/SCSS/Less, C/C++, Java, Python, Rust, Go, C#, Kotlin; Angular and Vue are not offered: typescript-lsp maps only ts/js extensions; CSS/SCSS/Less (`vscode-css-language-server` from npm `vscode-langservers-extracted`, `--stdio`, markers `*.css`/`*.scss`/`*.less`) has no official plugin, so the app ships the local marketplace `astrolabe-lsp` (`lsp-marketplace/`, plugin `css-lsp` with `lspServers`), written by `claude.plugin.ClaudePluginWriter` into `<dataDir>/lsp-marketplace`; React has no row, it is the optional catalog field `includes` on the TypeScript tool (`package.json` marker detects the project) shown as "Includes React" under its row in Tools and Languages (`includesNoteOf`). `ToolProbe` reports MISSING/INSTALLED/RESPONDING/FAILED (`ExecutableLookup` searches PATH first, then well-known user bin dirs; version via `CommandRunner`, tools without versionArgs are not run for a version; LANGUAGE_SERVER kinds get an LSP initialize/shutdown handshake over stdio by `LspHandshake`, timeout counts as INSTALLED; `ShimLaunch` runs Windows .cmd/.bat shims via `cmd.exe /c`; process trees are killed with `ProcessTree`; statuses are cached for `astrolabe.toolchain.status-ttl`, `probeAll` cached, `probeAllFresh`/`probeFresh` bypass). `ToolInstallService` takes only a tool id: plans (blocked without prerequisite or without a command for the OS), runs the argv through the PTY runner in the temp dir under one install lock, streams the whole output so far to the callback, re-probes fresh (`STILL_MISSING` = installed but not on the running app's PATH). `TechnologyDetector` (pure, bounded breadth-first scan, depth, folder and entry limits in `ToolchainProperties`, nested modules found at any folder name, markers: file name, `*.ext`, `package.json#dep`) and `ProjectToolsService` (rows per project, `enableLsp`/`disableLsp` via `PluginService`, adds the official marketplace first, every LSP plugin (official marketplace or the own `astrolabe-lsp`) is enabled in the project's overlay `settings.json` (see `overlay`); a group may override the LSP set of its members (`GroupLspService`, `group_lsp_override`); after `enableLsp` it writes the managed note `lsp-navigation` (resource `toolchain/lsp-navigation.md`: use the built-in LSP tool, grep only for text) into the overlay `instructions.md` through `preset.apply.LocalClaudeMdNote`, and `disableLsp` removes it only when no other LSP plugin stays enabled (user scope counts); Run from repo root (use `./gradlew`; Git Bash or PowerShell `.\gradlew.bat`).

```sh
./gradlew run          # launch the desktop app
./gradlew test         # JUnit 5 tests
./gradlew build        # compile + test + jar
./gradlew packageMsi   # installer for the current OS (packageExe also on Windows; packageDeb / packageDmg elsewhere; must run on that OS)
```

The `compose.desktop` block points `javaHome` at the Java 25 toolchain; without it `run` uses Gradle's own JDK.

## Clean code

- Constructor injection; immutability (`final`, records, unmodifiable collections); no `null` collections; `Optional` only as a return type.
- Tunables in `@ConfigurationProperties`, never `@Value`; no magic numbers/strings.
- Composables: stateless where possible, state hoisted, one screen per file, UI holds display logic only — work goes in Spring services.

## Conventions

Git:
- Commits and PRs carry no AI attribution: no `Co-Authored-By: Claude …`, no "Generated with Claude Code". The author is the git user only.
- Commit only when asked.
- Branches: `main` is stable; all development and testing happens on `develop`.
- Commit message is a single line: `<type>(ver. X.Y.Z): <description>`. Types, first match wins: `fix` (bug fix, error handling, race/order/state problems, guards against wrong behavior; async/sync rewrites that change execution flow) → `feature` (new user-visible capability, component, guard, endpoint, behavior) → `refactor` (restructure with provably identical behavior) → `chore` (dependencies, configs, env, manifests) → `ci` (pipelines, build/deploy scripts). Unsure fix vs refactor → `fix`; unsure feature vs refactor → `feature`.
- Version: every commit raises the PATCH in `version` of `build.gradle.kts` (X.Y.Z → X.Y.Z+1) and uses the new value in its message; MINOR and MAJOR are raised only when the user says so (then patch resets to 0). Never invent a version.
- Description: English, imperative, no trailing period, max ~80 chars, describes the behavioral/structural change, not code mechanics. 1 change = 1 clause; 2–3 related changes comma-separated. Preferred verbs: add, remove, fix, prevent, ensure, guard, await, sequence, replace, extract, rename, migrate, introduce, drop, restore, handle, wrap, unify, split, merge.
- Forbidden in description: improve, enhance, adjust, tweak, modify, change, optimize, better, cleanup, misc, various, several, some; bare "update" as the main verb; version bump / release X.Y.Z / file names like package.json; meta-mentions of imports, types, signatures.
- Example: `feature(ver. 1.0.0): add home view with project overview`

Code:
- Naming: `*Service`, `*Properties`, `*Configuration`, `*Repository`; Composables in PascalCase, files named after the main Composable (`HomeView.kt`).
- Tests: JUnit 5 + AssertJ + Mockito; one test class per production class; descriptive method names.
- Code and comments in English; UI text is English until localisation is decided.
