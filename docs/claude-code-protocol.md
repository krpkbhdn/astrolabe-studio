## 1. Hook events  (https://code.claude.com/docs/en/hooks)

Full list (33): SessionStart, Setup, UserPromptSubmit, UserPromptExpansion, PreToolUse, PermissionRequest, PermissionDenied, PostToolUse, PostToolUseFailure, PostToolBatch, Notification, MessageDisplay, SubagentStart, SubagentStop, TaskCreated, TaskCompleted, Stop, StopFailure, TeammateIdle, InstructionsLoaded, ConfigChange, CwdChanged, DirectoryAdded, FileChanged, WorktreeCreate, WorktreeRemove, PreCompact, PostCompact, PreModelSwitch, PostModelSwitch, Elicitation, ElicitationResult, SessionEnd.
(Unknown event name in settings = "Settings Warning", entry skipped, rest of file kept.)

### Common stdin fields (all events)
session_id; prompt_id (UUID of current user prompt = OTel prompt.id; absent before first input); transcript_path (written async, may lag - use last_assistant_message on Stop); cwd (follows cd/worktree); scratchpad_dir (2.1.257+, optional); permission_mode (`default`(=Manual)|`plan`|`acceptEdits`|`auto`|`dontAsk`|`bypassPermissions`); effort {level: low|medium|high|xhigh|max} (tool-context events); hook_event_name; agent_id (present only INSIDE subagent / in-process teammate); agent_type (agent name, e.g. Explore / custom; present with `--agent` OR inside subagent; subagent overrides session --agent). `model` only on SessionStart (optional). No $CLAUDE_MODEL env.
Tool events add: tool_name, tool_input, tool_use_id. File paths absolute, backslashes on Windows. MCP tools: optional `mcp_server` {name, source} (2.1.274+). MCP tool naming `mcp__<server>__<tool>`.

### Notification.notification_type (exact semantics)
- permission_prompt: tool-use approval or sandbox network request prompt **has waited ~6 s** (timer restarts on each keystroke in terminal; in SDK/Desktop hosts fixed ~6s, not deferred by typing; disable with CLAUDE_CODE_DISABLE_PERMISSION_PROMPT_NOTIFY_HOOKS=1)
- idle_prompt: Claude finished ~60 s ago, user hasn't typed, no background agent running
- auth_success; elicitation_dialog (form, user idle ~6s); elicitation_url_dialog (~6s); elicitation_complete; elicitation_response
- agent_needs_input / agent_completed: only relevant to agent view (`claude agents`) background sessions; agent_needs_input also for team-teammate setup question / auto-mode classifier cost notice (idle ~6s)
- quota_auto_resume_fired / _stale / _disabled (2.1.234+); plugin_notification (from mods)
- Shares timing with desktop notifications: **in a focused terminal you may never get permission_prompt promptly (~6s delay, and "mostly when you appear away")**. Use PermissionRequest for instant detection.
- Example sample: {"message":"Claude needs your permission","title":"Permission needed","notification_type":"permission_prompt"} (illustrative, not documented constants). Message strings are NOT stable.

### Exit codes (all command hooks)
0 = success; stdout parsed as JSON only if it is exactly ONE JSON object (else plain text; plain text becomes context only for UserPromptSubmit, UserPromptExpansion, SessionStart, PostModelSwitch). 2 = blocking error, stderr is reason, overrides JSON (exceptions: PermissionRequest, Elicitation/ElicitationResult). Any other = non-blocking error (first stderr line shown) unless onFailure:"block".
Universal JSON output: continue (false stops Claude entirely), stopReason, suppressOutput, systemMessage, terminalSequence (OSC 0/1/2/9/99/777 or BEL only; interactive only). additionalContext/systemMessage/initialUserMessage/stdout capped 10,000 chars. hookSpecificOutput requires hookEventName. Misplaced top-level fields silently ignored (see debug log "Hook JSON output had unrecognized keys").

## 2. Handler types (https://code.claude.com/docs/en/hooks, /hooks-guide)

Structure: `hooks[Event] = [ { "matcher": "...", "hooks": [ handler, ... ] } ]`.
Common handler fields: type (command|http|mcp_tool|prompt|agent), if (single permission-rule string like "Bash(git *)"; ONLY evaluated on Pre/PostToolUse, PostToolUseFailure, PermissionRequest, PermissionDenied - elsewhere hook never runs), timeout (seconds; defaults 600 command/http/mcp_tool, 30 prompt, 60 agent; 30 on UserPromptSubmit/Pre+PostModelSwitch; 10 MessageDisplay), statusMessage, once (skill frontmatter only).
Matcher: `*`/""/omitted = all; only [A-Za-z0-9_- ,|] = exact or list split on | or ,; otherwise JS regex (unanchored). FileChanged/StopFailure: only `|`.
Matching hooks run in parallel; identical handlers across settings files dedupe.

- command: {type, command, args[] (exec form, no shell; on Windows must be real exe not .cmd/.bat), async:bool, asyncRewake:bool (bg; exit2 wakes Claude), shell:"bash"|"powershell" (default bash, or powershell on Windows w/o Git Bash), onFailure:"continue"|"block" (2.1.295+)}. Shell form uses sh -c / Git Bash / PowerShell. async:true => timeout not enforced, cannot block.
- **http**: {type:"http", url (req), headers:{k:"Bearer $VAR"|"${VAR}"}, allowedEnvVars:[names] (only listed vars interpolated; others -> empty string), timeout, onFailure:"continue"(default)|"block"}.
  - Request: POST, Content-Type: application/json, body = same JSON as command stdin.
  - Response: 2xx + empty body = success; 2xx + JSON object = parsed with same output schema as command hooks; 2xx non-JSON/plain text = non-blocking error, NOT added to context; non-2xx = non-blocking error; **connection failure = non-blocking (action continues)**; timeout = canceled. Blocking needs 2xx JSON with decision fields, or onFailure:"block".
  - No `async` field documented for http (UNVERIFIED whether http supports background; docs list `async`/`asyncRewake` only under command). Keep server fast/respond immediately; default timeout 600s would hang a turn if server stalls - **always set a short `timeout` (e.g. 2-5)**.
  - Admin knobs: allowedHttpHookUrls, httpHookAllowedEnvVars (managed settings). Example from docs: url http://localhost:8080/hooks/pre-tool-use.
  - Not allowed handler type for SessionStart: only command and mcp_tool (so http cannot observe SessionStart!). UNVERIFIED for other events' restrictions beyond this; docs mention Setup also skips mcp_tool.
- mcp_tool: {server, tool, input{"${tool_input.file_path}" substitution}}; skipped on SessionStart at launch and Setup.
- prompt: {prompt ($ARGUMENTS placeholder), model, timeout, continueOnBlock}; LLM must return {ok, reason, impossible?}.
- agent (experimental): same prompt/model; subagent up to 50 turns, returns {ok,reason}.
- Concurrency: >12 prompt/agent hooks queue.
- Background-after-decision: for command hooks, print decision first then background with redirects.

## 3. Injecting hooks per launch without touching user files (https://code.claude.com/docs/en/settings, /cli-reference)

- `claude --settings <path-or-inline-json>`: "Values override the same keys in settings.json files for this session. Keys you omit keep their file-based values." Must be a regular file <= 2 MiB. Precedence (high->low): managed > **--settings (command line)** > .claude/settings.local.json > .claude/settings.json > ~/.claude/settings.json. Can set any key user settings can; cannot set Managed/Global-config keys (~/.claude.json keys).
- **Lists merge** (e.g. permissions.allow). For `hooks`: identical handlers across files run once; hooks from --settings are ADDED alongside user/project hooks (docs state merge rule for list keys; the hooks-specific merge is implied by "Identical handlers in multiple settings files run once" - treat as additive; UNVERIFIED by experiment). Plan: verify with a smoke test that user's own hooks still fire AND yours fire.
- `--setting-sources user,project,local`: restricts which file sources load (does NOT affect --settings). `--safe-mode` disables all hooks except managed. `--bare` skips hook auto-discovery (then only --settings hooks apply). `--restricted` loads only managed + --settings.
- disableAllHooks setting kills hooks (not managed ones unless set in managed). allowManagedHooksOnly blocks user/project/local/plugin hooks - **check `claude doctor`/settings for it on managed machines; --settings hooks may then be ignored** (UNVERIFIED whether --settings counts as blocked; docs say it blocks "user/project/local/plugin").
- Edits to settings files are hot-reloaded in running sessions (hooks included); ConfigChange fires.
- Hooks do NOT re-run on --resume transcript replay.
- Env alternatives: none for injecting hooks. `env` block in settings can set env vars. Per-session env must go on the process env when spawning.
- Settings JSON shape:
```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash|Edit", "hooks": [
        { "type": "http", "url": "http://127.0.0.1:PORT/hook", "timeout": 5,
          "headers": { "X-CCM-Session": "$CCM_SESSION" }, "allowedEnvVars": ["CCM_SESSION"] }
      ] }
    ],
    "Stop": [ { "hooks": [ { "type": "http", "url": "http://127.0.0.1:PORT/hook", "timeout": 5 } ] } ]
  }
}
```
- Windows quoting: pass a **temp file path** (`--settings C:\Users\...\ccm-xxxx.json`), not inline JSON (cmd/PowerShell/ConPTY quoting of `"` is fragile). Delete after session ends; file can be read when launched (re-read on change since watched) so keep it for the session lifetime.
- Identify session in hook: payload carries session_id; to map hook -> your tab before session_id is known, pass your own id via env var (CCM_SESSION) + header with allowedEnvVars, or pre-assign `--session-id <uuid>`.

## 4. CLI (https://code.claude.com/docs/en/cli-reference, /headless, /setup)

Commands: `claude`, `claude "q"`, `-p`, `-c/--continue`, `-r/--resume <id|name|path.jsonl>`, `update`, `install [version|stable|latest]`, `auth login|logout|status` (status = JSON, exit 0 logged in / 1 not; `--text`; fields authMethod none|claude.ai|oauth_token|api_key|api_key_helper|third_party, configDirectory (2.1.268+)), `doctor` (read-only diagnostics, no session), `mcp` (+ `mcp login|logout <name>`), `plugin(s)`, `agents` (agent view; `--json` prints active sessions array, `--json --all` incl. completed bg sessions; `--cwd <path>`; requires TTY to open UI), `attach <id|name>`, `logs <id|name>`, `stop|kill <id>`, `respawn <id>`, `rm <id>`, `daemon status|logs|run|stop`, `purge [path]`, `remote-control`, `setup-token`, `ultrareview`, `gateway`, `import`, `auto-mode defaults|config|reset`. `--version/-v` prints e.g. `2.1.211 (Claude Code)`.

Flags relevant to a GUI manager:

- --model (alias sonnet|opus|haiku|fable or full ID), --effort low|medium|high|xhigh|max|ultracode, --fallback-model, --advisor.
- --add-dir (not restored on resume - pass again), --worktree/-w [name|#PR] (+ --tmux), --agent <name>, --agents '<json>' (or file path with -p, 2.1.281+), --append-system-prompt[-file], --system-prompt[-file], --append-subagent-system-prompt (-p only).
- --mcp-config <files|strings>, --strict-mcp-config, --plugin-dir, --plugin-url, --settings, --setting-sources, --bare, --safe-mode, --restricted, --ide, --chrome/--no-chrome, --debug[=filter], --debug-file <path>, --verbose, --teammate-mode, --remote-control/--rc [name], --bg/--background (background agent; not with -p; `--bg --exec cmd`), --desktop.

- NOTE: for an interactive TUI embedded in a PTY, none of the stream-json flags apply; hooks are the observation channel. stream-json -p mode is an alternative (structured, but then you render the UI yourself and permission prompts go via --permission-prompt-tool / SDK control requests).

- Resuming a session that is still running as a background session attaches to it.
- Since 2.1.302: `claude -p` starts in Manual mode when nothing sets a mode.

### Detecting installation
- Native installer: macOS/Linux/WSL `~/.local/bin/claude` (symlink -> `~/.local/share/claude/versions/<ver>`); Windows `%USERPROFILE%\.local\bin\claude.exe` (+ `%USERPROFILE%\.local\share\claude`). Auto-updates in background.
- npm: `@anthropic-ai/claude-code` (Node 22+, installs the same native binary; shim name on Windows likely claude.cmd - UNVERIFIED, docs only say binary is linked by postinstall). Homebrew cask `claude-code` / `claude-code@latest`; WinGet `Anthropic.ClaudeCode`; apt/dnf/apk packages `claude-code`.
- Strategy: resolve `claude` via PATH (`where claude` on Windows; try claude.exe, claude.cmd), fall back to `%USERPROFILE%\.local\bin\claude.exe`, then run `claude --version` (parse `^\d+\.\d+\.\d+`), `claude auth status` (JSON), `claude doctor` for health. Feature-gate flags on version (many flags 2.1.2xx+).
- Env controlling updates: DISABLE_AUTOUPDATER=1 (background only), DISABLE_UPDATES (blocks all), CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE.

## 5. Environment variables (https://code.claude.com/docs/en/env-vars, /hooks)

Passed to hooks/subprocesses: CLAUDE_PROJECT_DIR (session-start dir; unchanged by worktree), CLAUDE_PLUGIN_ROOT/DATA, CLAUDE_PLUGIN_OPTION_<KEY>, CLAUDE_EFFORT, CLAUDECODE=1, CLAUDE_CODE_CHILD_SESSION=1 (nested session detection), CLAUDE_CODE_REMOTE ("true" web only), CLAUDE_CODE_BRIDGE_SESSION_ID, CLAUDE_CODE_MESSAGING_SOCKET/TOKEN (per-session; cannot be set via settings env), **CLAUDE_ENV_FILE only for SessionStart, Setup, CwdChanged, FileChanged** (not PowerShell hooks; writes of `export NAME=value` persist into later Bash commands). ## 6. On-disk data (https://code.claude.com/docs/en/claude-directory, /sessions, /sub-agents)

Root = `~/.claude` (= `%USERPROFILE%\.claude` on Windows; `CLAUDE_CONFIG_DIR` overrides everything under it).
- Transcript: `~/.claude/projects/<project>/<session-id>.jsonl`; `<project>` = absolute cwd with every non-alphanumeric char replaced by `-` (e.g. `C--Users-Bohdan-Work-Code-Personal-cc-manager`; >200 chars truncated to 200 + hash). One JSON object per line (message / tool use / metadata). Format internal, version-unstable - parse defensively.
- Subagent transcripts: `projects/<project>/<session-id>/subagents/…` (path given as agent_transcript_path in SubagentStop). Large tool outputs: `<session>/tool-results/`. `.orphaned-<ts>-<suffix>.jsonl` / `.jsonl.superseded-<ts>` = set-aside copies, not in picker (ignore).
- `~/.claude/sessions/`: one small file per RUNNING session, removed on exit, crash leftovers cleared next launch (used by CC to detect concurrent sessions/crashes). File format UNVERIFIED - candidate for liveness/crash detection; inspect on disk.

## 7. Statusline contract (https://code.claude.com/docs/en/statusline)

Config: `"statusLine": {"type":"command","command":"<script or inline>","padding":0,"refreshInterval":N(seconds,min 1)}`. Can be supplied via --settings. Runs on events (new assistant message, mode change, etc.), debounced; add refreshInterval for idle periods. Script reads JSON on stdin, prints text (ANSI ok, multi-line ok). **A custom statusline hides most footer hints** (esc to interrupt etc.) - side effect for users; and it REPLACES the user's own statusLine if you set it via --settings (key override, not merge). Prefer hooks unless you need cost/context.
Stdin fields: model.id, model.display_name; cwd == workspace.current_dir; workspace.project_dir, workspace.added_dirs[], workspace.git_worktree?; cost.total_cost_usd (client-side estimate, resets on /clear), cost.total_duration_ms, cost.total_api_duration_ms; context_window.context_window_size, used_percentage, remaining_percentage, current_usage{token counts of last API call}; exceeds_200k_tokens; fast_mode; effort.level?; thinking.enabled; prompt_cache{warm, caching_observed, ttl, expires_at, requests, misses, expected_rebuilds, hit_ratio, cache_write_tokens, miss_recache_tokens, last_miss_at, last_miss_cause, miss_causes, recache_tokens_if_cold} (2.1.251+); session_id; session_name?; prompt_id?; transcript_path; version; output_style.name; vim.mode?; agent.name?; pr{review_state, kind?}; worktree{name,path,branch?,original_cwd,original_branch?}; rate_limits{five_hour{used_percentage,resets_at}, seven_day{...}, spend_limit{used_percentage,resets_at,used_usd?,limit_usd?,period?}} (only claude.ai Pro/Max or gateway; only after first API response; each window may be absent). resets_at = epoch seconds.

## 8. Recommended per-session status mapping

Subscribe (http hooks, short timeout): SessionStart*, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PostToolUseFailure, Notification, SubagentStart, SubagentStop, Stop, StopFailure, PreCompact, PostCompact, SessionEnd, Elicitation, ElicitationResult, (optional ConfigChange/CwdChanged/TaskCompleted).
*SessionStart rejects http handlers per docs (only command/mcp_tool) -> use an exec-form `command` handler (the app's own launcher with `args`) for SessionStart, or skip and infer start from the first event / from pre-assigned --session-id. Note SessionStart/Setup hook events are also emitted in stream-json.

State machine (main agent only: IGNORE events where agent_id is present for status, track them as subagent children):
- IDLE: initial after SessionStart (any source) ; after Stop ; after StopFailure (mark IDLE+error badge with `error` enum; rate_limit/overloaded are retryable) ; after SessionEnd => ENDED.
- WORKING: UserPromptSubmit ; PreToolUse / PostToolUse / PostToolUseFailure (main-agent) after a pending state - these resume WORKING; SubagentStart (inc. count); PreCompact (until PostCompact).
- NEEDS_USER_ACTION: PermissionRequest (instant, preferred; no tool_use_id - correlate by tool_name+time) ; Notification.notification_type in {permission_prompt, elicitation_dialog, elicitation_url_dialog, agent_needs_input} ; Elicitation event (until ElicitationResult).
  Clear NEEDS_USER_ACTION -> WORKING on the next PostToolUse / PostToolUseFailure / PreToolUse of a different tool_use_id / ElicitationResult / UserPromptSubmit. If the user denied the permission: no PostToolUse(Failure) fires for permission denials ("does not fire ... for permission denials") -> then Claude usually continues with new tool call or Stop; a following Stop/PreToolUse/UserPromptSubmit resolves it. Hook-based apps cannot see the denial itself (UNVERIFIED if a PermissionDenied hook fires for manual denials - docs say PermissionDenied is auto-mode classifier only).
- idle_prompt (~60s after finish): state already IDLE; use only as "waiting for you" nudge / badge.
- Plan approval (ExitPlanMode) and AskUserQuestion: NOT documented as Notification types. ExitPlanMode / AskUserQuestion are tools -> they surface as PreToolUse (tool_name ExitPlanMode / AskUserQuestion) and likely PermissionRequest for ExitPlanMode (UNVERIFIED). Practical rule: on PreToolUse with tool_name in {AskUserQuestion, ExitPlanMode} set NEEDS_USER_ACTION until the matching PostToolUse (tool_use_id) arrives. Also `permission_mode` field in payloads reveals plan mode (`plan`).
- Edge cases:
  - **User Esc-interrupt does NOT fire Stop** (docs: Stop doesn't fire on user interrupts); PostToolUseFailure with is_interrupt:true "for an abort" but "cancelling a running tool doesn't fire this hook". So an interrupted turn can leave you stuck in WORKING. Mitigations: (1) detect Esc yourself in the PTY input layer (you own the keystrokes) and set IDLE; (2) idle_prompt after 60s as safety net; (3) tail transcript mtime / last record for an interrupt marker (format UNVERIFIED); (4) next UserPromptSubmit resets anyway.
  - API error ends turn -> StopFailure (not Stop). Always handle both.
  - Stop fires at every turn end, even if background tasks pending: check Stop.background_tasks[] / session_crons[] non-empty => "IDLE but background work in flight / will self-wake" (show as WORKING-background or distinct state). A Stop-hook block (decision:block) re-continues; don't block from the manager.
  - Subagents: events with agent_id are the subagent's; main Stop only after subagents done (SubagentStop precedes). SubagentStop.agent_type "" = internal helper (ignore).
  - Compaction: PreCompact/PostCompact (trigger auto|manual) -> WORKING only while compacting (PreCompact sets it, PostCompact clears it; neither opens or closes a turn, so an auto compact of an idle session returns to IDLE and one mid-turn stays WORKING until Stop).
  - Process crash / kill / terminal close: no hooks guaranteed. SessionEnd runs on exit, /clear, resume switch, and SIGTERM, but with 1.5s budget; a hard crash fires nothing. Use PTY child exit as the authority, plus `~/.claude/sessions/` leftover files (UNVERIFIED format).
  - /clear: SessionEnd(reason clear) then SessionStart(source clear) with NEW session_id -> same tab, rekey. `/resume` in-session: SessionEnd(resume) then SessionStart(resume). Compaction fires SessionStart(source compact). Fork: SessionStart(fork).
  - HTTP hook failures are non-blocking: if manager is down, Claude continues; on manager restart you've lost state -> resync from transcript tail or wait for next event.
  - Hook payload `permission_mode` gives live mode (default/plan/acceptEdits/auto/dontAsk/bypassPermissions) per event.
  - Notification delay: permission_prompt only ~6s after the prompt shows (and typing resets it) - so don't rely on it alone for fast "needs action" UI; PermissionRequest is the immediate signal.
  - In `claude -p`/SDK hosts, permission prompts go through canUseTool/--permission-prompt-tool, not the TUI.

## 9. Windows specifics (https://code.claude.com/docs/en/setup, /hooks)

- Native Windows supported (Win10 1809+). No sandboxing on native Windows (WSL2 only).
- Shell: Git for Windows (Git Bash) is OPTIONAL; with it, Bash tool uses Git Bash (and Monitor tool needs it); without it Claude uses the PowerShell tool. CLAUDE_CODE_GIT_BASH_PATH (e.g. C:\\Program Files\\Git\\bin\\bash.exe) if not found. CLAUDE_CODE_USE_POWERSHELL_TOOL=0/1.

Exec form (`command`+`args`) must be a real .exe (no .cmd/.bat), e.g. `"command":"powershell.exe","args":["-NoProfile","-ExecutionPolicy","Bypass","-File","..."]` or `curl.exe`. http hooks avoid all shell issues -> preferred on Windows.
- PTY: docs do not mention ConPTY/PTY requirements for hosting `claude`; it is a native exe (Node not needed even for npm install) using a TUI (alternate-screen "fullscreen" renderer by default? CLAUDE_CODE_NO_FLICKER=1 enables fullscreen; CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1 = classic renderer). Hosting in ConPTY is standard practice but UNVERIFIED in docs (VS Code/JetBrains/Desktop host it themselves). Verify terminal-config page (https://code.claude.com/docs/en/terminal-config - NOT read) for TERM/Shift+Enter/ keybinding needs.
- Paths in hook payloads use backslashes (file_path in Write/Edit/Read). Transcript dir name for `C:\Users\Bohdan\Work\...` = `C--Users-Bohdan-Work-...` (':' and '\' -> '-').
- --settings: prefer file path; inline JSON needs `\"` escaping and differs between cmd, PowerShell 5.1 and Start-Process/CreateProcess arg quoting. When using ProcessBuilder/ConPTY with an argv array there is no shell, but the Windows command-line round-trip still mangles quotes -> use file.
- Installed binary: `%USERPROFILE%\.local\bin\claude.exe` (native) - may not be on PATH inside a GUI-spawned process; resolve absolute path yourself.
- Reading transcripts: Windows path-encoding and CRLF not an issue (JSONL written LF; UNVERIFIED).
- Env: Hooks inherit your process env; pass CCM_* variables in the spawn env and list them under allowedEnvVars for header interpolation.

## 11. Agent teams: `--agents`, subagent model and effort (claude 2.1.310, Windows 11)

Docs: https://code.claude.com/docs/en/sub-agents. Verified for real with `RealAgentTeamTest` (see below).
- `--agents '<json>'` is a JSON object `{ "<name>": { "description", "prompt", ...frontmatter fields } }`. `description` (required, tells the lead when to delegate) and `prompt` (the subagent's system prompt) are the core; `tools` (array of tool names, or comma string in `.md` frontmatter; omitted = inherit), `model` (`sonnet|opus|haiku|fable|inherit` or a full id), `effort` (`low|medium|high|xhigh|max`), `maxTurns`, `permissionMode`, `skills`, `mcpServers`, `hooks`, `memory`, `background`, `isolation` and more. Unknown fields are ignored. Names must not start with `-` and cannot contain `:`. Priority: managed > `--agents` > `.claude/agents` > `~/.claude/agents` > plugins, so a role with the same name as a project agent file wins.
- Interactive sessions: `--agents` takes INLINE JSON only; a file path is accepted just with `-p` (2.1.281+). It works together with `--settings <file>` and in a pty4j ConPTY session.
- Windows quoting: pty4j joins arguments into a command line and only wraps ones that contain a space in quotes, WITHOUT escaping inner quotes. The raw JSON therefore failed with `Invalid --agents configuration: invalid JSON: JSON Parse error: Expected '}'`. An argument that already starts with `"` is passed through untouched, so `WindowsArgument.quote` applies the CommandLineToArgvW rules (wrap in quotes, `\"` for quotes, double the backslashes before a quote or the end) and it works, including newlines in the prompt. Other platforms get the plain argument array.
- Per-subagent MODEL works: lead `--model opus --effort high`, role `tester` with `"model":"haiku"`; the subagent transcript (`SubagentStop.agent_transcript_path`, written a moment after the stop) holds `"modelId":"claude-haiku-5-5"` (an attachment of type `model`), while the statusLine of the lead reported `Opus 5.5` / `high`.
- Per-subagent EFFORT works natively (the `effort` field, 2.1.292+ also a per-invocation parameter that wins over the field): hook events raised inside the subagent (`PreToolUse`, `PostToolUse`, `PostToolBatch` with `agent_id`) carried `"effort":{"level":"low"}` for the tester while the lead ran `high`. There is no per-subagent thinking field; subagents inherit the main session's. `CLAUDE_CODE_EFFORT_LEVEL` beats both; the launcher does not set it.
- Delegation: the lead received the roster through `--append-system-prompt` (the lead role's prompt, then one line per role `- name: description`, told to delegate with the Agent tool and `subagent_type` = role name). With the task "Ask the tester role to read the first line of settings.gradle.kts with the Read tool" the lead called `Agent` with `subagent_type: "tester"`; hooks showed `SubagentStart/Stop` with `agent_type: "tester"`, the subagent's own `Read` call carried its `agent_id`. Hooks from `--settings` and the user's own user-level hooks (additionalContext on SubagentStart) both fire inside subagents.
- Initial prompt: a positional argument after `--` (so a task starting with `-` is no flag) is submitted as the first turn of the interactive session; no PTY typing is needed.
- The lead's own model and effort come from the lead role through the usual `--model` / `--effort` flags; the lead role is NOT in `--agents` (it is the main session).
- Plain launch and resume: `launch(projectId, mode, team)` adds `--agents`, `--append-system-prompt` and the mode flag (`--continue` / `--resume`) without a task; the flags are not persisted in the transcript, so they are passed again on every launch. The project's `ModelSelection` wins per field over the lead role's selection.
- Subagent `tools` syntax (sub-agents docs, tools-reference): built-in tool names (`Read, Write, Edit, NotebookEdit, Glob, Grep, LSP, Bash, PowerShell, WebFetch, WebSearch, Agent, Skill, TodoWrite`, ...), a whole MCP server as `mcp__server__*` (or a single `mcp__server__tool`), and `Agent(type)` only for a `--agent` main thread. Permission patterns such as `Bash(git *)` are NOT documented for `tools` (only in `disallowedTools`, where they drop the whole tool), so the app accepts only names and `mcp__server__*` (`RoleDraft.isToolEntry`). Omitting `tools` inherits everything; if no entry resolves the subagent fails to launch. Some tools never reach subagents (`AskUserQuestion`, `EnterPlanMode`, `ExitPlanMode`, `ScheduleWakeup`, `Workflow`, ...).

## 12. Plugins, marketplaces, MCP servers and skills (claude 2.1.310, Windows 11)

Backend in package `extension` (`PluginService`, `McpService`, `SkillService`); every CLI call goes through `ClaudeCli` (cwd = project directory for project/local scope, arguments quoted with `WindowsArgument` on Windows so JSON survives).

A local directory marketplace (the app's own `cc-manager-lsp`) is registered with `claude plugin marketplace add <dir>`, at user scope by the app.
- Plugins: `claude plugin list --json` is an array `{id: "name@marketplace", version, scope: user|project|local, enabled, installPath, projectPath?}` (project/local entries carry `projectPath`); `--available` adds `{installed, available: [{pluginId, name, description, marketplaceName, installCount}]}` (~3900 entries, fetched once and cached). `plugin marketplace list --json` is `[{name, source: github|url|..., repo|url|path, installLocation}]`. `plugin details <id>` is plain text (Description, `Component inventory` lines `Skills (2)  a, b`, `Always-on: ~177 tok`), parsed tolerantly.
- Changes: `plugin install|uninstall|enable|disable|update <id> --scope <s> --json`, `plugin marketplace add <source> --scope <s> --json`, `marketplace remove <name>`, `marketplace update [name]`. `--json` runs are non-interactive, so a marketplace-declared command is never run on its own: the result carries `shownCommand` (with `sha256`) and nothing is installed. ## 13. Subagent lifecycle and opening an agent (claude 2.1.310; docs-verified, not driven in a live TUI)

- Why agents looked finished while working: the old reducer closed every subagent on the parent's `Stop`. A background agent (`Agent`/`Task` tool with `run_in_background: true`, or an agent with `background: true`) returns at once with "Async agent launched", the parent turn ends with `Stop`, and the agent keeps running until its own `SubagentStop` (same `agent_id`). Fix: `Stop`/`StopFailure`/Esc close only agents not known to be background; a background agent ends only on `SubagentStop` or a `SessionStart` that is not a compaction.
- Background detection is by agent id: the parent's `PostToolUse` of `Agent`/`Task` for a background launch carries a `tool_response` such as "Async agent launched successfully ... agentId: <id>" (parsed tolerantly; also requires the "Async agent launched" text or `tool_input.run_in_background`). That exact id is marked background, whether its `SubagentStart` came before or after. Foreground calls get their `PostToolUse` only after the agent ended, so they are never marked. UNVERIFIED against a live payload: the exact text of `tool_response`.
- Per-agent state from events carrying `agent_id`, only while the agent is running: `PreToolUse` = running that tool (`Bash: <command>`, `Edit: <file>`), `PostToolUse` = thinking, `PermissionRequest`/attention `Notification` = needs action until its next tool event, `PostToolUseFailure` marks the last tool failed. The session is red when the main agent or any running subagent waits; agent events never clear the main agent's wait. `SubagentStop` ends the agent: FAILED when the last tool failed or `last_assistant_message` starts with "API Error" (a heuristic, there is no error field), else DONE; INTERRUPTED comes from Esc on a non-background agent.
- A background agent whose `SubagentStop` never arrives is not closed: after `cc-manager.sessions.subagent-stale-after` (default 10m) without events it is shown dimmed as "No activity for N" and no longer keeps the session WORKING (a silent agent that waits for the user still keeps it red); any new event of that agent revives it.
- Transcripts: `SubagentStop.agent_transcript_path`; while running the file is already at `<parent transcript without .jsonl>/subagents/agent-<agent_id>.jsonl` (parent path = `transcript_path` of `SubagentStart`; the id must match `[A-Za-z0-9_-]{1,64}`). Lines are JSON with `type` user/assistant/attachment/..., `message.content` a string or blocks `text`, `thinking`, `tool_use{name,input}`, `tool_result{content}`. The app reads only the tail of files whose real path is under `~/.claude/projects`.
- Claude's own agent panel (docs: code.claude.com sub-agents / keybindings / commands): rows under the prompt, Up/Down move, Enter opens the transcript, `x` stops or dismisses, Esc returns; `/tasks` lists background work and runs immediately even mid-turn; `/agents` only prints a reminder on 2.1.310. Finished successful agents leave the panel at once and stay in `/tasks` for 30 s.
- Decision: the app never injects keys or commands into Claude's terminal to open an agent, because it cannot see a draft the user may be typing. Clicking an agent opens the app's own read-only log (live for running agents); "Show session in terminal" only selects the session tab and focuses the terminal.
- Second signal: `Stop` (and `SubagentStop`) carry `background_tasks[]` with entries like `{id, type: "subagent", status: "running"}`; every subagent listed there as running is marked background and kept running on `Stop`, even when its launch call was not seen (resumed session, agent defined with `background: true`). When a background agent ends while the lead is idle, the lead is woken to handle the result, so `SubagentStop` of a background agent reopens the lead's turn (WORKING) until the next `Stop`. UNVERIFIED against a live payload: the exact `background_tasks[]` entry shape (taken from another session's observation).

## 19. Session history search (package `history`, transcripts under `<claudeConfigDir>/projects/<encoded cwd>/<session-uuid>.jsonl`)

- One JSON object per line. Read fields: `type` (`user`, `assistant`; others are skipped), `uuid` (line id), `sessionId`, `cwd`, `timestamp` (ISO-8601), `message.content` (a string, or blocks: `text`, `tool_use` {id, name, input}, `tool_result` {tool_use_id, content: string or `[{text}]`}). Subagent transcripts (`<session>/subagents/*.jsonl`) are not indexed. The session UUID is also the file name stem and is preferred over the line's `sessionId`.
- The indexer reads from the stored byte offset in batches of whole lines (an unfinished last line waits for its newline); a file whose last indexed byte is not a newline, or that shrank, is read again from the start; files that vanished are forgotten; paths must resolve inside `<claudeConfigDir>/projects`.
- Secrets: text is masked (`SecretFilter.mask`), and a `tool_use` whose full input (before the 400 character cut) touches a sensitive file or dumps the environment is not indexed, nor is its `tool_result`.
- Resume uses `claude --resume <uuid>` (valid UUID only) in the transcript's `cwd` if that folder is inside the project, else in the project folder; `--mcp-config`, `--settings`, `--plugin-dir` and `--add-dir` are passed again.
- Directory names: Claude names a project's folder under `<claudeConfigDir>/projects` by replacing every non-alphanumeric character of the absolute project path with `-` (`C:\a b` becomes `C--a-b`). This is lossy (`a-b`, `a b` and `a\b` collide) and Claude may truncate very long paths. `TranscriptIndexRepository.evictProject` relies on it only for transcripts without a `cwd`: it compares the folder name with the encoded project path (exact, case-insensitive on Windows), so a collision or a truncated name can match the wrong project or none.
- Fail closed: the ids of sensitive `tool_use` blocks are kept per file so their `tool_result` lines are skipped. When more than `max-sensitive-tool-ids` (default `1000`) are pending, `TranscriptIndexer` clears the set and stores the marker `*`, after which every later `tool_result` of that file is skipped.
- Keys: `cc-manager.history.scan-interval` (default `30s`) and `cc-manager.history.max-entries` (default `200000`; the oldest files are evicted over the limit and not indexed again).

## 20. Context breakdown via `/context` (package `usage.context`, claude 2.1.319, Windows 11, verified by hand)

- `claude -p /context` prints the real per-category breakdown as markdown and makes no model call (cost 0, about 3-5 s). `ContextBreakdownService.measure` runs it through `ClaudeCli.execute` (argv, no shell) only when the context dialog opens or is refreshed; it is blocking, so callers use a background thread. Results are cached per session id (or folder) for `cc-manager.context-breakdown.ttl` (default `60s`, `force` bypasses); `cc-manager.context-breakdown.timeout` defaults to `30s`.
- With a session id: `claude -p --resume <id> --fork-session --no-session-persistence /context` gives the real Messages row of that transcript. The fork is never saved (checked: no new `.jsonl` under `~/.claude/projects`), so `--continue` and the history indexer do not see it. Without an id the output is a fresh-process estimate from the folder's CLAUDE.md, MCP, plugins and skills (`approximateMessages`). Not tested: against an id that is live in a pty4j terminal at that moment.
- The service runs only plain `/context` (in 2.1.319 headless `/context all` prints the same). Output without the breakdown is a failure and is never retried: a retry could reach the model as a paid call. The session id must be a canonical UUID, else the call fails before any process starts. Concurrent calls for one key share one process (single-flight); failures are cached for `cc-manager.context-breakdown.failure-ttl` (default `10s`) so reopening the dialog does not respawn processes; expired entries are evicted on each store. Rounded values and `~` items are approximate (item sums do not equal their category). The breakdown keeps the full markdown (`raw`) and every other `### ` table with a readable last-column amount as `otherSections`, so richer output of a later version still shows.
- cwd must be the session's folder (worktree folder for isolated tasks), else the transcript is not found and memory files and agents differ. No `--settings` and no `CCM_SESSION`, so the process never registers as a session; the user's own SessionStart hooks do run, and the folder's stdio MCP servers are started on every measure. The measurement also runs without the app-injected `--agents`, `--append-system-prompt`, `--mcp-config` and `--plugin-dir`, so sessions started with a team (or the Assistant) are under-reported. Measuring an id that is live in the pty is untested.

- Parsing (`ContextBreakdownParser`): header `**Model:**` and `**Tokens:** used / window (p%)`; sections split on `### `: "Estimated usage by category" (name, tokens, percentage), "MCP Tools" (tool, server), "Custom Agents" (type, source), "Memory Files" (type, path), "Skills" (skill, source); unknown sections are ignored. Token cells: `599`, `2.3k`, `1m`, `~90` (approximate), `< 20` (20, approximate). The format is not a stable API; the service returns a failure text instead of throwing.
- UI: the `ContextMeter` chip sits in the status bar for the selected session tab (yellow above 50%, red above 70%, `contextLevel`); above 70% a blinking `CompactAlert` shows "Context N% - compact?" with a Compact button that types `/compact` into the session (refused with the usual reason while the session is busy) and a dismiss x, re-armed once the level drops. ## 21. Code Mode (package `codemode`, claude 2.1.323, hiding mechanisms verified by hand)

- Idea: instead of exposing many MCP servers' tools to the model, the app gives the session one extra MCP server `cc-manager-code` (`CodeModeEndpoint`, `/code-mode/<ccmSessionId>` on the HookServer, same per-session bearer as the project server, own path so `cc-manager` never lists its tools) with three tools: `list_servers` (eligibility and problem per server), `search_tools` (`ToolCatalog`/`ToolSearch`, ranked, TypeScript-style signatures from `TypeScriptSignatures`, limit `search-limit`) and `execute` (JavaScript, the body of an async function; tools are `servers.<server>.<tool>(args)`; result parsed JSON or text, structured content wins, images saved as files under the data dir and returned as `{type:'image', mimeType, path}` (at most `max-images-per-session` (50) images and `max-image-bytes-per-session` (100 MiB) per session; past those caps the call fails with a script error, while a single image over 10 MiB, of an unsupported type or with invalid data is returned as `{type:'image', mimeType, omitted: <reason>}` without a path), output capped at `max-output-chars` and marked truncated). A script error is returned as a tool error with the console output.
- Per-session client pool: `ServerConnections` holds, per `ccmSessionId`, one `McpClient` per eligible server (`StdioMcpClient`, `HttpMcpClient` over `JsonRpcMcpClient`, created by `McpClients`), connected lazily by `search_tools`/`execute`, closed when idle for `idle-client-close` (sweep) or when the session ends (`closeSession`); the tool catalog survives idle close and the next call reconnects. Eligible: user, local, or approved project (`.mcp.json`) servers read by `McpConfigReader.definitions` (precedence local > project > user), and servers of enabled plugins (below); a server needing OAuth sign-in is reported "needs sign-in" and not retried. Each tool call from a script runs on its own thread with its own limit `tool-call-timeout` (below `timeout`): past it the call fails with "timed out ... the connection to the server was reset", the client is closed (which ends the stuck request) and the next call reconnects, so a stuck server never holds a sandbox worker or delays shutdown. Only transport failures, timeouts, over-limit responses and sign-in errors reset the connection; an ordinary JSON-RPC error answer of a healthy server (`McpServerErrorException`, e.g. invalid params) keeps the client and its state and its message goes to the script as the tool error. An open client is re-checked against the candidates every `candidate-recheck-ttl`: no longer eligible (approval revoked, removed) closes it and refuses the call, a changed definition closes it and refuses that call, the next one reconnects. Ended session ids are remembered up to 10000 (oldest dropped) so a late call cannot recreate a pool, and a forgotten session's `SessionImages` refuse further writes. The candidate lookup (`ServerCandidates`) is separate from the pool.
- Discovery and names: the `initialize` result of `cc-manager-code` carries per-session `instructions` (`CodeModeEndpoint.instructionsFor`, computed at each initialize from the session's candidate aliases without connecting; `McpJsonRpcServer.respond` takes a supplier): "Code Mode is on in this project. These MCP servers are routed through Code Mode and their tools are NOT available directly: <aliases>. To use any of them, or when a tool or server of this kind is missing or unknown (for example mcp__plugin_playwright_playwright__* or a name like playwright), do not start or call it yourself: call list_servers (names, status), then search_tools (TypeScript signatures), then execute with a JavaScript script that calls `await servers.<alias>.<tool>(args)`. Chain many calls in ONE execute and return only a small result; write big data to files instead of returning it. Images arrive as {type:'image', path}. servers.<alias> also accepts the saved name shown by list_servers." Names are sanitised (`PromptText`: no control, bidi or format characters), each cut at 40 characters, at most 20 listed ("and N more"); no servers or an ended session give the generic text. The three tool descriptions repeat that the servers are reachable only through Code Mode. A server answers to its script alias, its saved name (`servers.plugin_playwright_playwright`) and the Claude tool-prefix forms (`mcp__<name>` and `mcp__<name>__<tool>`) alike: `ServerConnections.resolve` for `ScriptBridge`, the `search_tools` `server` filter and `list_servers`; the script side gets the accepted spellings and the alias list at run start (`HostBridge.serverIndexJson`, `__servers` in the GraalJS prelude, `servers` field of the container `run` message) so `servers.nosuch` and `servers.nosuch.x()` fail at once with "Unknown server 'nosuch'. Available in Code Mode: playwright, ... Use list_servers." (no index, as in a bare test bridge, means no check); an unknown tool of a known server fails with "Unknown tool 'x' on server 'playwright'. Did you mean: <up to 5 closest names>. Use search_tools." Aliases stay frozen per session and TypeScript signatures print the alias. `list_servers` prints one line per server: alias, "saved as <name>" when it differs, scope (user, project, local, plugin), transport, then connected, ready (connects on first use) or unavailable with the reason.
- Hiding the original servers (Claude must not also see them): the launcher passes a `CodeModeAccess` to `HookSettingsWriter` for single-project sessions of a project with Code Mode on. Verified on claude 2.1.323: for servers declared in the project `.mcp.json`, `disabledMcpjsonServers` in the `--settings` file stops them from starting at all and hides their tools; for user/local servers there is no such switch, so `permissions.deny: ["mcp__<server>"]` removes their tools from the model, but claude still starts the process. `--strict-mcp-config` is not used because it would also drop the app's own `cc-manager` and `cc-manager-code` servers (they come from `--mcp-config`) and the user's other servers, which Code Mode does not manage. Names are validated only for hiding (`CodeModeAccess`: `[A-Za-z0-9_-]{1,100}`, `cc-manager*` reserved), so a hostile `.mcp.json` name cannot inject a rule and is just not hidden; the saved project list accepts any `NameRules` name. Plugin servers (scope `PLUGIN`, `extension.mcp.PluginMcpServers`, read-only, never listed on the MCP page or by `McpService.servers`): per Claude's plugin docs a plugin's servers live in `<installPath>/.mcp.json` (bare map or `{"mcpServers":...}`) and in `mcpServers` of `.claude-plugin/plugin.json` (inline map, `.json` path, or an array mixing them; later names replace earlier ones; `.mcpb` bundles are not read), `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` (`<config>/plugins/data/<id with other characters as ->`) and `${CLAUDE_PROJECT_DIR}` expand in command, args, env, url and headers besides the usual `${VAR}`/`${VAR:-default}`. A plugin counts only when enabled. Managed settings (`/etc/claude-code/managed-settings.json`, `/Library/Application Support/ClaudeCode/managed-settings.json`, `ClaudeCode/managed-settings.json` under Program Files; `managed-settings.d` drop-ins and server-managed settings are not read, a known limitation) decide alone when they name the plugin. Otherwise the repository settings (`<session dir>/.claude/settings.json`, then `settings.local.json`, later wins) can disable it, but enable it only when a project or local install entry of it names this project (that is how Claude records project installs) or `<config>/settings.json` enables it too, so a hostile repo cannot re-enable a plugin the user installed but disabled. Its install comes from `<config>/plugins/installed_plugins.json` (version 2): user entries always, project/local entries only when their `projectPath` equals the session's working directory or the registered project folder (so a task-worktree session still sees the main project's installs; paths normalised, case-insensitive on Windows), the most specific scope then the newest `lastUpdated`, missing folders and ones with `.orphaned_at` skipped; `${CLAUDE_PROJECT_DIR}` is the session directory. A malformed entry (invalid path characters, wrong JSON types, null) or file drops only itself, never the project's other servers. `.mcp.json`, `plugin.json` and a manifest `mcpServers` path must be relative and resolve, symlinks followed, inside the install folder, otherwise they read as empty; an entry with neither `command` nor `url` is dropped; the `${CLAUDE_PLUGIN_DATA}` folder (`<config>/plugins/data/<sanitised id>`) is created, and only when a server of the plugin references it. Naming: Claude calls the tools `mcp__plugin_<plugin>_<server>__<tool>`, so the name saved in `project_code_mode` is the canonical `plugin_<plugin>_<server>` (characters outside `[A-Za-z0-9_-]` become `_`); it passes `NameRules` and is exactly the `permissions.deny` entry (`mcp__` + name) the launcher already writes for every saved server, with no `disabledMcpjsonServers` entry (that switch does not apply to plugin servers, the process still starts, tools hidden; verified in a spike). Scripts use the friendly alias `servers.<server key>` (`ServerCandidates.Candidate.name`, used by list_servers, search_tools, signatures, `ScriptBridge` and both sandbox preludes, which only ever see this name), falling back to the canonical name when the key is not usable or another configured server (plugin or not) would have the same alias. The alias map is frozen per session at its first list/search/execute (kept in the `ServerConnections` pool), so a script's names never change when the configuration changes mid-session; only new sessions re-resolve it, and a catalog entry and client of a server that stops being eligible are dropped. A canonical name that two plugins (`a.b` and `a_b`, the same plugin from two marketplaces) or a plugin and a user, local or project server resolve to makes all of them ineligible with the reason "ambiguous name" (shown in the settings rows and by list_servers), so nothing is silently dropped or shadowed and the deny rule never hides one of them behind the other; `Candidate.stored` is the saved name, `ServerConnections` keys clients by alias and checks the saved list through `stored`. Eligible = plugin enabled and definition readable; plugin servers need no approval, HTTP ones needing sign-in are ineligible via the health name `plugin:<plugin>:<server>`; a plugin update changes the install path and with it the definition, so the identity re-check closes the client and the next call reconnects. A saved plugin server whose plugin is disabled or uninstalled shows under "Saved but not found any more" and is reported `not found` by list_servers. A saved server that is not eligible (not approved, needs sign-in) stays checked on the settings page with a warning (launch still hides it, but it cannot run in Code Mode). `search_tools` and `list_servers` are pre-allowed; `execute` is not.
- Sandboxes (`ScriptSandbox`, chosen in Settings, `code_mode_isolation` row, `CodeModeSandboxes`): GraalJS in-process (`GraalJsSandbox`: polyglot context with no host access, only the `HostBridge`; limits `statement-limit` and the hard cap `max-script-time`; has NO heap limit, a script allocating without bound can exhaust the app's memory, so it is the weakest isolation) and Docker or Podman (`ContainerSandbox`: throwaway container from `cc-manager.code-mode.image` with no network, read-only filesystem plus a 16 MiB `/tmp` tmpfs mounted `noexec,nosuid`, no mounts, no capabilities, `container-memory` with `--memory-swap` equal to it (no swap), `container-cpus`, pids limit, `no-new-privileges`, user `nobody`, `--rm`, `--pull never`, label `ccm-code=<instanceId>` (first 16 hex of SHA-256 of the absolute data dir, `CodeModeSandboxes.instanceId`) so containers a crashed run left behind are killed at the next start, only this instance's (`ContainerRuntimeDetector.killStaleContainers`; it runs only when the saved backend is DOCKER or PODMAN, only for that runtime and only if it responds, on its own thread so it never delays session cleanup or start), and an in-container `timeout -s KILL` watchdog of `max-script-time` plus a grace period that ends the script even when the app is gone). The container protocol: the runner (`code-mode/runner.js`, base64 in env `CCM_RUNNER`, started as `node -e`) and the script travel as JSON lines over stdin/stdout; the app sends `run` (code) and a `result` per call, the container sends `call` (id, server, tool, args), `log`, `done` and `error` lines; the app answers each call through the `HostBridge` and kills the container on timeout or an over-long line (4 MiB). `ContainerRuntimeDetector` finds the runtime and whether the image is present (a successful runtime and image check is reused by `CodeModeService` for `environment-check-ttl`, 30s; a backend change or a failed check drops it); the image is pulled only by the explicit button in Code Mode settings, never on start; it must provide `node` and a `timeout` binary (BusyBox or coreutils, so not a distroless image). A container backend that is unavailable makes `execute` fail with the reason, never fall back to GraalJS silently.
- Security model: (1) `execute` itself goes through Claude's normal permission flow, so the user sees the script in the app's permission dialog via the `PermissionRequest` hook (held proposal); (2) each tool call from a script passes `ToolCallGate`: a tool that is read-only and not explicitly destructive (destructive hint absent or false) runs at once, everything else (including tools with no annotations) holds a `PermissionProposal` through `ProposalService.holdForApp` with the server, tool and an `ArgumentPreview`, answered in the same dialog; the wait is bounded only by the proposal service's own `cc-manager.hooks.decision-hold` (there is no second approval timeout); two suggestions add per-session grants (memory only, dropped when the session ends; every grant is bound to the server's `McpServerDefinition` and `ServerConnections` calls `ToolCallGate.forgetServer` whenever it drops a server, refuses it for a changed definition or finds it ineligible, so a changed `.mcp.json`/user config, a plugin update or a reused alias never inherits a grant, and a restart after a failed call keeps it): "Allow <tool> for this session" and "Allow ALL tools of <server> for this session, including ones marked destructive" (the user's explicit broad choice: covers later calls of every tool of the server, destructive ones included, because real servers such as Playwright MCP mark every non-read-only tool destructiveHint true; shows how many tools were already allowed; session-scoped, never persisted; a tool declaring destructiveHint true never gets the per-tool grant and a per-tool grant is not honoured for a tool that declares itself destructive at call time (a reconnect may re-list it so), only a one-time allow or the server grant covers it; neither is offered or honoured when the preview was cut or sanitised); deny, timeout, no open approval or any failure of the question denies (an `Error` such as OutOfMemoryError is not swallowed). `ArgumentPreview` masks values under secret-looking key names (token, password, secret, authorization, api key, cookie, credential, bearer, private key, session, jwt, passphrase, signature) and secret-shaped strings (`Bearer ...`, `sk-...`, `ghp_...`, JWT, long mixed base64/hex tokens), replaces control, format (bidi, zero-width) and line/paragraph separator characters in the label, keys and strings with a space (`PromptText.withoutHidden`; `list_servers` and `search_tools` names likewise), keeps distinct keys distinct (` (2)` suffix; the key `...` is reserved for the overflow marker) and cuts long strings (200 characters), big objects/arrays (20 members) and deep nesting, each cut with an explicit marker ("N more fields", "... N more items", "... [M more characters]"); when anything was cut, replaced or renamed the "allow for this session" suggestion is not offered and a call of a tool that was granted earlier is asked about again, because the hidden part could be the harmful one; (3) `CodeModeAudit` (`code_mode_call`, V29) records project, session, server, tool, decision kind, status and duration, never arguments or results; rows older than `audit-retention` are deleted; (4) kill switch: `ExecutionRegistry` knows the running script of each session (at most one; every registration carries a deadline, `timeout` plus the approval wait, never past `max-script-time`: a second `execute` within it is refused with "A script is already running in this session (started N s ago, limit M s, K s left)...", one past it by more than 5 s cancels the old run and replaces it, so a session never stays busy for good; the cancel also resets the MCP client of a blocked call and the requester detaches from a worker that ignores the interrupt after the 2 s grace, releasing the registration anyway), the UI shows a stop chip (`ui/codemode/StopScriptChip`) that cancels it (sets the cancelled flag, interrupts the runner thread, so no further tool call starts; once the script has finished the cancel is a no-op, and a stop keeps the output printed so far within a 2 s grace). The same cancel runs when the session goes IDLE or ends: Claude fires no Stop on Esc, `SessionRegistry.markInterrupted` turns WORKING into IDLE, and the session listener of `CodeModeSessionCleanup` then cancels the session's running script, which withdraws its open approval proposal too (the interrupted wait dismisses it). The hook worker queue can lag, so an IDLE reading is re-read once after `idle-cancel-delay` and cancels only if still IDLE, and a session the registry does not know yet is neither cancelled nor cleaned up while a script runs; only OFFLINE cancels at once. A client that abandons the HTTP request (Claude Code gives up on a slow `tools/call` with its own `The operation timed out.`, a DOMException text that appears nowhere in this app) cannot be observed: the JDK `HttpServer` offers no disconnect callback, so the script keeps running until its deadline or Stop, and a script waiting for the user's approval counts up to `cc-manager.hooks.decision-hold`. MCP `notifications/cancelled` is handled per request, see the next bullet. Cleanup of ended sessions (client close, file deletion) runs off the hook worker thread, one session at a time; remembered working directories of sessions that never called a tool or whose spawn failed are forgotten by the launcher and by the same sweep; (5) Sandbox boundary: GraalJS's boundary is the polyglot context options (`allowAllAccess(false)`, `IOAccess.NONE`, no native access, threads, processes or environment, `HostAccess.EXPLICIT`, no host class lookup), so the script reaches only the `HostBridge`. For the container the boundary is the container itself (read-only root, no network, no capabilities, memory and pids limits, `/tmp` tmpfs `noexec`). `runner.js` builds the script's `servers` and `console` inside a Node `vm` context from strings, so `require`, `process` and `module` are undefined there; that is defence in depth, not a proof against `vm` escapes (Node documents `vm` as no security mechanism), and a script that escaped it would still be inside the container.
- Claude's own limits on the `execute` call (client side, so its text is `Error: The operation timed out.`, not ours): for HTTP servers each request times out after 60 s unless the server entry carries a `timeout` in ms (docs mcp.md: `"timeout": 600000`; overrides `MCP_TOOL_TIMEOUT` for that server, hard wall-clock, progress does not extend it) and a call without response or progress is aborted after `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` (5 min, a per-server `timeout` >= 1000 is a floor on it). `HookSettingsWriter` therefore writes `"timeout"` = `max-script-time` plus 30 s into the `cc-manager-code` mcp entry, so our own limits fire first and name themselves. When Claude abandons a call (Esc, its own timeout) it should send the MCP notification `notifications/cancelled` with `params.requestId` (not confirmed on the wire for Claude Code): `CodeModeEndpoint` tracks the JSON-RPC ids of in-flight `execute` calls per session (`InFlightRequests`, at most 256, removed when the call ends; ids are compared as JSON so `1` and `"1"` differ, one session can never cancel another's) and a matching notification cancels that request's `RunCancellation` (handed to `ExecuteTool` through the request thread), which stops only the run that request starts: a cancel that arrives before the run is registered (sandbox/runtime checks) stops it as soon as it registers and before the script starts, a refused second `execute` or a late cancel of a finished request never touches another run; unknown or finished ids are ignored and the notification gets no response. Without a cancel, a new `execute` while the previous script waits on an unanswered tool question is refused with "A script is waiting for your approval of <server>.<tool> in cc-manager: answer or deny the dialog, then retry" (`ApprovalWait.openTool` through `ExecutionRegistry`), never cancelling the waiting one.
- Names and lookups: a server whose name is not `[A-Za-z0-9_-]{1,100}`, is reserved or starts with `mcp__` is ineligible ("name not allowed in Code Mode"), plugin aliases the same, so a configuration cannot spoof a requester or inject a rule; names and tool names shown in dialogs, errors and `list_servers` are capped with `ServerNames.shown`. App-held proposals carry `PermissionProposal.Origin` (HOOK, ASSISTANT, CODE_MODE) and the dialog's requester line (`requesterOf`) reads it instead of parsing the tool name. `ServerConnections.resolve` uses the last candidate scan while it is younger than `candidate-recheck-ttl` and rescans only for a name it does not know, so a script of N calls does not rescan the configuration N times; `search_tools` with a `server` filter resolves it first and starts only that server.
- Persistence and config: V29 `project_code_mode` (project, enabled, servers JSON), `code_mode_isolation` (single row, default `GRAALJS`) and `code_mode_call`; V30 rebuilds `project_preset_component` to allow kind `CODE_MODE` (`CodeModeApplier` applies a preset component by writing the project setting; validated by `PresetComponentValidator`; the assistant tools `add_preset_component` accept kind CODE_MODE with `servers`). Keys `cc-manager.code-mode.*` (`CodeModeProperties`): `timeout` (10m, the script limit enforced by `CodeModeService`; the time the user spends answering tool questions is not counted), `max-script-time` (1h, the hard cap of a whole run that the sandboxes enforce as their own timeout), `tool-call-timeout` (3m, one remote tool call, excludes the approval wait; capped at `timeout`); the nesting is `tool-call-timeout` < `timeout` < `max-script-time`, sized for browser automation (first `npx` launch, navigation, screenshots), and each error text names the limit that hit, its value and the property to raise, `environment-check-ttl` (30s), `max-images-per-session` (50), `max-image-bytes-per-session` (104857600), `statement-limit` (100000), `max-output-chars` (20000), `search-limit` (10), `idle-client-close` (10m), `image` (`node:22-alpine`, placeholder to pin by digest), `container-memory` (256m), `container-cpus` (1), `audit-retention` (30d), `candidate-recheck-ttl` (5s), `idle-cancel-delay` (2s). UI: project settings page `Code Mode` (`ProjectCodeModeState`, enable and choose servers with their eligibility), Settings page `Code Mode` (backend, runtime detection, image pull), `ui/codemode` rows and stop chip, preset kind dialog.
- Limits and non-goals (v1): group sessions and the Assistant never get Code Mode; JavaScript only (no TypeScript, no other languages); a plugin server shows up only through its own plugin (a plugin's marketplace-level or managed servers, `.mcpb` bundles and `userConfig` substitutions are not read); tool calls inside a script run sequentially (no parallel `Promise.all` fan-out to one client); no OAuth sign-in from the app; changes to the toggle, the saved servers and the enabled plugins apply to sessions launched afterwards (a running session keeps its launch-time hiding and alias names), while the eligibility and definition rechecks of an open session still apply.

## Per-session credential

URLs carry only the session id: `/hook/<ccmSessionId>`, `/statusline/<ccmSessionId>`, `/mcp/<ccmSessionId>`. The credential `HMAC-SHA256(runSecret, ccmSessionId)` (base64url) travels in `Authorization: Bearer <cred>` and is compared with `MessageDigest.isEqual` against the HMAC of the id in the path; a missing, wrong or other session's token (or the token in the URL) gets 404. It is written literally into the session's settings and mcp files and into an owner-only `<id>.token` file (`HookSettingsWriter.writeOwnerOnly`: POSIX 600, Windows owner-only ACL; all deleted with the session), because the Left-arrow agent view makes the supervisor restart claude with a foreign environment while `--settings` and `--mcp-config` paths survive. `CCM_HOOK_TOKEN` is still set in the env of the session's claude process (`ClaudeCommand.environment/groupEnvironment`, stripped by `terminalEnvironment` for shells and runs) but only as the helper's fallback.
- http hook handlers: `"headers":{"Authorization":"Bearer <token>"}` with the literal token (no `allowedEnvVars`; URLs are not interpolated).
- SessionStart (http not allowed): exec form, `{"type":"command","command":"<launcher>","args":["--post-hook","<url>"],"async":true}` (documented: with `args` the command is spawned directly, no shell, each element one argument, on Windows `command` must be a real .exe; `shell` is ignored). Field names confirmed at code.claude.com/docs/en/hooks. In dev `args` also carries the JVM options, `-cp`, `HookPoster` and the flag. statusLine (shell string only): on Windows Claude runs it through Git Bash if installed, else PowerShell, and Git Bash eats backslashes and splits on spaces, so `HookHelperCommand` uses forward slashes and the 8.3 short path of launcher and class directory (`WindowsShortPath`, GetShortPathNameW through `java.lang.foreign`), which needs no quoting in either shell. Without a short name (8dot3 disabled) it falls back to a double-quoted path that works in Git Bash only; `shellFormNote()` says so for the UI. No launcher path at all: statusLine and SessionStart are omitted, `unavailableReason()` tells why. `HookPoster` (java.base only, 1 s connect + 2 s read timeouts, loopback, no redirects) reads stdin bytes and the token from the file named by `--token-file <path>` (placed right after the URL by `HookHelperCommand`), falling back to `CCM_HOOK_TOKEN` in its environment (exit 1 plus one stderr line when both are empty, nothing sent; the same for a missing URL or one that is not http on a loopback host), posts with the bearer, and exits 0 even if the server is gone or answers non-2xx (one short stderr line, never the token). Measured in dev: about 0.06 s per call; packaged mode (launcher with the full jpackage classpath) not measured. The token never appears in a command line, so there is no curl version gate. Gates: the SessionStart exec form (`args`, added in Claude Code 2.1.139 per the changelog; an older claude ignores `args` and would run the bare launcher, i.e. start the app) is written only when `claude --version` is known and >= 2.1.139 (`ClaudeVersion.atLeast`), otherwise SessionStart is omitted and the statusLine stays. On Windows a statusLine string whose launcher path still needs quotes after shortening is written only when Git Bash is present (`CLAUDE_CODE_GIT_BASH_PATH` set, or `bash.exe` beside the `git.exe` on the PATH); otherwise, and for paths with `$`, a backtick or `"`, the statusLine is omitted and `unavailableReason()` says why. `ui/Main.kt` treats `--post-hook` only as the first argument and `HookPoster` exits 1 quietly for a missing or invalid URL, so a mismatched launch never starts Spring or Compose.
- Project `--mcp-config` file: `"headers":{"Authorization":"Bearer <token>"}` (literal) on `cc-manager`.
- Verified live (claude on Windows): `RealMcpToolTest` (a tool call reaches the project MCP server, so `${VAR}` in headers of a `--mcp-config` file is expanded), `RealClaudeLaunchTest` (SessionStart (then via curl) makes the session IDLE, http SessionEnd makes it OFFLINE), `RealRateLimitTest` (statusLine post, then via curl), `ClaudeHookSmokeTest` (http hooks).
- Every launch with generated settings goes through `ClaudeLauncher.start`, which always sets the fallback variable (`HookSettingsWriterTest.onlyTheLauncherWritesSessionFilesSoEveryLaunchGetsTheTokenVariable` guards that no other class writes such files). Residual: the files and env are readable by same-user processes (and by claude's own Bash tool, so a prompt-injected session can leak its OWN token, never another's); the helper command line holds the token file path, never the token.
